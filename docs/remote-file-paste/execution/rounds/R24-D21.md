## 4. 慢 ACK / 暂停消费者 / 取消 / 子进程退出

- **慢 ACK**：对端完全不回时泵 8 次仍恰好 2 块在途、`PendingBytes=524288`（`==MaxPendingBytes`）且**不再读字节**；逐条补 ack 时每条只放行 1 块。
- **暂停消费者**：Core 闸门 64 次申请 → 2 活动/32 排队/30 拒绝（队列不无界）；浏览器暂停 drain 只接受 2 块，恢复一次 drain 恰好 2 条 ack。
- **取消**：浏览器缓冲 0、`releasedBytes=524288`、dispose 后残留 0；Core pending 0/0、3 个源各释放恰好 1 次。
- **子进程退出**：Chromium pid 消失 + `pgrep=0`；Core 子进程 exit 0、无残留；收尾零命中。
- 服务进程 RSS **仅观测不设阈值**（观测到 −113 MB，噪声含 V8/zstd/分配器保留页）。

## 5. Core 清理所有权

自有字节源在**取消/失败/超时/Dispose** 路径恰好释放一次；`Dispose()` 释放活动槽位、**排队中**的目标也一并撤销、重复 Dispose 幂等。结论：协调器对"已准入的源"负全责，**"排队"同样是占用闸门位置**。

## 7. 顺带修掉的两处真实产品缺陷（最小修复）

1. **`AttachmentTransferCoordinator.cs:210,227`**：批次 `Cancelled` 后 `PendingBytes/PendingChunks` 仍报 2×256 KiB（状态机镜像保留历史块）⇒ **取消后资源读数永远脏**，外部监控会以为窗口仍被占用。修复：批次终态为 Cancelled（或未开批）时返回 0（对端不会再 ack，窗口语义上已释放），逐文件历史仍可从镜像读取。
2. **`AttachmentTransferCoordinator.cs:1081`（+`_gateQueued` 记账）**：`ReleaseGateSlot()` 只看 `_gateHeld`，漏掉"**已排队未获槽位**"的目标。症状：b 排队时 a 释放把 b 提升为活动，此刻 b 被 Dispose（导航/取消）⇒ **该全局并发槽位永久泄漏**（实测 Dispose 后 `Gate.ActiveCount` 仍为 1）。修复：排队也记账，释放时一并撤销。
3. **采样口径修正（影响判据有效性，非产品代码）**：`Runtime.getHeapUsage().usedSize` **不含** ArrayBuffer/Blob 的 backing storage（30 MiB 的 `Uint8Array` 只让 usedSize 动 4 KB）⇒ 浏览器内存读数改为 `usedSize+backingStorageSize`（否则**反例 N6 会是假绿**）；Core 托管堆改为 GC+终结器+连读 3 次取最小，并把紧判据限定在**隔离**的 D21 用例集进程（共享全量跑实测斜率 131 KB/轮、包络 11.2 MB；隔离跑 25.9 KB/轮、0.75 MB）。
