## 5. 发现：一处**上游缺陷**（notRun，需外部决策）

**失效 ready receipt 被服务端确定拒绝后，composer 既不移除陈旧草稿、也不呈现该拒绝**——发送前后可见的错误行完全相同，卡片仍显示 ready。归属锁定依赖 `@deepseek-ai/dsh-client-ui-conversation` / `dsh-client-ui-attachment`，**仓库侧无法最小修复**，故按上游兼容缺口记录、不擅自改 `node_modules`。

影响：用户会看到"发送没反应"而不是"这份草稿已失效，请移除后重新导入"。方案 §4.2 明确要求"宿主重启后旧 ready receipt 可能失效；此时提示用户移除失效草稿后重新导入"——即**提示缺失**这一条当前不可达。与 R09 的情况同类：属外部依赖能力缺口，需要一次明确决策（登记等上游 / 在插件侧自行补一个可取消的提示位 / 接受该 UX 缺口）。

## 6. 顺带修掉的夹具自身缺陷

1. `fault-proxy` 的 `stall` 曾**消费请求体**，导致 release 后转发空体 → 改为不读体、挂起真实连接。
2. `fault-proxy.close()` 曾因 keep-alive 连接**死锁** → 改为先 `closeAllConnections` 再等 close，并加 5 s 兜底。

## 附：失效 receipt 提示链路的追加复核（R22b，结论**推翻** §5）

R22 的 §5 判定"原生恢复提示不可见"是**错的**。按用户指定的观测面重做后：**提示确实可见**，R22 漏读有三处具体原因。

### 一、决定性证据

- **元素**：`<div role="alert" class="_toast_e5v0f_6">`，**portal 到 `document.body`**（不是 composer 内）。
- **文案**：**"文件尚未上传成功，请重新添加后再试"**。
- **生命周期**：`holdMs=3000 + fadeMs=1000 = 4000 ms`；MutationObserver 实测 **4001 / 4002 / 4002 ms**（三次独立运行一致）；首个非空采样在发送后 **+1852 ms**（`samples[12]`），消失边界 +5653 ms 有 → +5806 ms 无。
- **采样全貌**：114 条中 **25 有 / 89 空**；发送前 12 条全空（+1 → +1699 ms），89 条空样本全部列在 JSON 的 `emptySampleSequence`。
- **独立于 DOM 的公开旁证**：页面自己发出的 `POST /remote/api/session/prompt` 响应信封（CDP Network 读取）为
  `{"result":{"ok":false,"error":{"code":"session/attachment-invalid","message":"File was not uploaded for this session.","details":{"reason":"FILE_NOT_STAGED"}}}}`。
- **截图**：页面顶部居中深色圆角 toast（左圆圈感叹号 + 上述整句正文）；composer 内文件芯片仍是 `d19p-stale-receipt.bin / BIN 2.0KB`、只有删除按钮、**没有"上传失败/重试"** —— 这正是 R22 把它当成"唯一可见错误行"的那一处。截图里另有一条 provider stub 的"本轮运行失败 …3901 failed"横幅，与本故障无关。

### 二、R22 为什么漏读（三处，选择器不在其中）

1. `d19-failure-gates.mjs:890-891` 是 **`poll` 后 `sleep(4000)` 的单点读取**，而 toast 恰在 **4000 ms** 卸载 —— 每次都读在卸载瞬间。
2. `readVisibleErrorLines` 用 `/失败|错误|无法|failed|error/i` 过滤 `innerText`，而该 toast 文案**不含其中任何一个词** —— 这个观测面对它**结构性失明**。
3. `[data-composer-card] [class*="notice"]` **恒不匹配**：那行 `div[role="status"].uV2eYG_notice` 是 composer 卡片的**兄弟**节点，且只用于 `level==="info"`。

### 三、归属更正

R22 说 `@deepseek-ai/dsh-client-ui-conversation` "没把拒绝呈现给用户"——**恰好相反**：它正是呈现该拒绝的包（渲染 `lib/client.js:15840`、reason→文案 `:15301`、zh 文案 `:13683`；错误起源在 `@deepseek-ai/dsh-api-session-controller/lib/index.js:930`；toast 由 `@deepseek-ai/dsh-web-frontend/dist/assets/index-BKQ_L1z6.js:61` 创建）。

### 四、"公开 `Session.promptError`"**没有公开读取路径**（据实记录，不伪造）

用户要求的这一观测面在当前组合下**不可达**：boot 后新增 25 个全局、298 节点对象图扫描、宿主侧 `grep promptError dsh-api-session-controller/lib/index.js` = 0、`remote.session.*` 13 个方法无一返回它、wire 契约只带 `{reason}`。因此证据 JSON 里该字段**逐样本恒为 `null`** 并标 `promptErrorReadPath:"none:no-public-handle"`；fiber 读取仅作**非公开旁证**（它驻留 ≥17 s，可解释 R22 为何漏读），**结论不依赖它**。替代的公开面是上面两条（toast DOM + 页面自身 prompt 响应信封）。

### 五、三项澄清（证据 JSON `clarifications`，逐条带 `file:line`）

1. **`staged` vs `ready`**：`staged` 是本插件**线协议** `import-result`/`batch-end` 的结果（`staged|failed|partial`），只表示"对端**草稿**已接收字节并给出 attachmentIds"，协议里**没有** `ready`（`src/shared/protocol.ts:106-107`、`src/shared/wire/session.ts:691-692`，产出点 `src/client/receiver.ts:1151`）；`ready` 是 **Harness 上传层**状态（`…ui-conversation…/client.js:3012/:3052` 写 `{status:"ready",receiptId,file}`，附件包消费 `…ui-attachment…/client.js:686`，并作发送前置 `:15823`）。**关键**：`staged` 不保证 receipt 仍有效——本轮芯片停在 ready 仍被 `FILE_NOT_STAGED` 拒。
2. **撤销请求位置**：`POST /api/pair/revoke {deviceId}` 删设备表项（`@linxin666/dsh-remote-web-ui/lib/index.js:306`，路由 `:1010`）。**新请求**被 `/remote/api` 门控在进 Host 前拒掉 → **403 + 信封码 `unpaired`**（`:1874`；谓词 `:592` 要求 live/non-revoked cookie），**不会是 `FILE_NOT_STAGED`**；**在途请求**（撤销前发出、停在门控前）放行时按当时门控转发，以同一 403/`unpaired` 结束（观测点 `tests/fixtures/fault-proxy.mjs:331 release()` 记 `outcome="released"` + `status=403`）；**客户端取消**是另一条路（`outcome="client-aborted"`）。撤销只废该设备凭据（心跳 401+`unpaired`，`:1343`），配对通道本身正常。
3. **`incomplete` 汇总口径**：`$incomplete = @($checks | ? status -eq 'incomplete')`；`$portableStatus` 在 `coreFailures>0 或 incomplete>0 或 用例数不符 或 failed>0 或 skipped>0` 时为 `fail`（`eng/verify-portable.ps1:788-791`）；incomplete 来自 Development `requiredChecks` 未实现层级（`:752-753`）或 Core 未覆盖项（`:758-761`），并入 `notCoveredByProfile`（`:819`）；**只有 incomplete 时仍 `exit 0`** 并打印"profile 自身范围通过；完整 Development 验证仍未完成"（`:841-846`）——四者并存是**设计如此**，不是矛盾。

### 六、我自己的检查也出过错（如实记录）

我先前断言"114 条采样非空为 0"是**误读字段名**：旧 JSON 用的是 `roleAlerts`/`promptErrorCode`，而我按 `alertText`/`promptError` 取值。旧文件真实情况是 **26/114 有 `roleAlerts`、103/114 有 `promptErrorCode`**。该文件的 schema 与我的规格不一致是诱因，但**结论性判断前我没有先核对字段名**，这是我的失误。

### 七、教训（写入交接文档）

涉及"提示/通知是否出现"的判据：① 必须**从动作之前开始**轮询并覆盖**完整瞬时窗口**，禁止 `sleep(固定值)` 后单点读；② **不得**用"错误关键词正则"作为唯一证据面（文案可能不含这些词）；③ 断言要**钉住出现与消失**（证明观测到生命周期而非静态字符串）；④ 注意 **portal 到 `document.body`** 的元素，别假设它在业务卡片内；⑤ 读状态前先**核对字段名**再下结论。

### 二、⚠️ 判据不稳定（本轮的决定性发现）

| 运行 | 结果 |
| --- | --- |
| 子代理自测 | 32/32 gates、10/10 负向探针、exit 0 |
| **我的独立直跑** | **31/32**：`T02-stale-receipt-native-prompt-visible` **FAIL** |
| 门禁 `resource-and-failure-suites` 内的再跑 | 32/32（通过） |

我的直跑中，T02 的 detail 显示**所有可见子条件都已满足**——文案="文件尚未上传成功，请重新添加后再试"、`portal=true`（parent=body 且不在 composer 卡片内）、观察起点无残留=true、出现=+155 ms、消失=+4158 ms、存活=4003 ms、命中样本=52/79、信封=`session/attachment-invalid`/`FILE_NOT_STAGED`——**却仍判 FAIL**。这说明断言里存在**未打印进 detail 的隐藏子条件**（很可能是"最后一次挂载之后必须出现安静采样点"这类依赖挂载次数/窗口边界的条件；子代理自测里也观察到同一次拒绝会挂载两次、可见区间有 4.0 s 与 7.5 s 两形态），或存在时序竞态。

**两点结论**：
1. **结论本身不受影响**：两次运行都独立观测到 portal 到 `document.body` 的 `[role="alert"]` toast、文案逐字正确、存活约 4000 ms、并与该次 `FILE_NOT_STAGED` 信封绑定 —— "原生恢复提示可见"成立，R22 的"不可见"确实是假阴性。
2. **判据不能算通过**：按方案"测试不稳需可控时钟/通道复现，不用延长 sleep 掩盖竞态"的纪律，**不稳定判据不得记为通过**；门禁里那次 `pass` 是**侥幸的一次绿灯**（证据文件被第二次运行覆写为 `result: pass`、`failedGateIds: []`、32 gates），因此 `resource-and-failure-suites` 当前的 pass 状态**不可信**，直到 T02 稳定。

### 三、剩余一步（下一轮）

1. 找出 T02 里**未打印的隐藏失败子条件**（把每个子条件单独打印出来，或让判据在失败时给出具体是哪一条），并**消除对挂载次数/窗口边界的依赖**——断言应只依赖"出现→消失→存活 ∈ 上界"，或对两次挂载都成立；
2. 用**可控方式**复现不稳定（例如把采样窗口边界与 toast 生命周期做成可注入参数），而不是延长 sleep；
3. 连续跑 **≥3 次全绿**后，才把 D19 记回 `done` 并复核 `resource-and-failure-suites`。

### 二、`Session.promptError` 的措辞更正（我此前的表述有误）

"公开接口"指的是**客户端插件获得的 Cordis `ctx`**，**不是** window 全局变量、也不是服务端 RPC。研究基线：

```js
const scope = ctx.sessions.scope(sessionId)
const session = scope && ctx.sessions.sessionOf(scope)
const error = session?.getSnapshot().promptError
```

### 一、T02 失败机制（先解释，后改断言）

### 二、子断言化（消除"明细全真、总判假"）
