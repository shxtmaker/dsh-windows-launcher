## 关键侦察结论（决定了实现与判据的形态）

1. **remote 的改写只对 `Headers` 实例 `set()` 设备头**：`att(init)` 在 `h instanceof Headers` 时 `h.set(deviceHeader, dv)`；否则走对象拷贝分支；若 headers 缺失则**完全不注入**。因此承载必须用 `new Headers(init?.headers)`。
2. **改写条件是同源 + `/api/` 前缀**（`so(url) && sf(url.pathname)`），`sf` 明确排除 `/api/pair/`、`/api/update/`、桥接路径。因此承载必须传**原始同源 `/api/...`**，预拼 `/remote` 会导致既不注入设备头、又被重复改写。
3. **device 凭据在调用时从 `sessionStorage` 读取**（`rdv()`），不是安装时快照。
4. **remote 的 boot 脚本在 loopback 上直接 `return`**（`h==='localhost'||'::1'||/^127\./`）。这是本轮最容易踩的坑：受控 harness 若绑在 `127.0.0.1`，改写层根本不存在，判据会假性失败。
5. **注入内容会被压缩**：实测承载脚本以 `var G="__DSH_FILE_UPLOAD__"` 形式出现，不是 `globalThis[...]`；remote boot 用 `w["__DSH_REMOTE_CHANNEL_BOOT__"]=seat` 赋值（同一脚本里还有 `delete w[...]`）。因此判据按"脚本正文含全局名/赋值语句"定位，而不是猜写法。
6. **上游未占用 `__DSH_FILE_UPLOAD__`**（已 grep 确认），因此该全局目前只有本插件安装。
7. **pnpm 按 tarball 路径缓存 `file:` 依赖的 integrity**：重新打包后同名路径不会被重新解析，夹具会继续跑旧 `lib/`。这导致本轮一度出现"代码已改但判据测的是旧产物"。

## 本轮修复的自身缺陷

1. **夹具跑的是旧构建产物**：pnpm 按 tarball 路径缓存 integrity，重新打包后 `dsh plugin add` 报 "added 0"，夹具里仍是 D03 的 `lib/`。新增 `install-plugin.sh` 显式清 lock 条目与模块后重装，并校验 `upload-hook.js` 存在。
2. **注入内容定位写错**：原按 `globalThis["__DSH_FILE_UPLOAD__"]` 查找，实际压缩后是 `var G="__DSH_FILE_UPLOAD__"`；remote boot 则是 `w["__DSH_REMOTE_CHANNEL_BOOT__"]=seat`（同脚本还有 `delete w[...]`）。改为按"脚本正文含全局名"与"赋值语句"定位。
3. **受控 harness 绑在 loopback 导致改写层不存在**：remote boot 脚本按设计在 loopback 直接 `return`。改为绑定 `lanAddress`（非 loopback）。
4. **U09 原先用模板字符串拼接脚本正文**，易受转义影响且语义不清。改为独立页面预置未知 hook，再用 `<script>` 元素追加执行承载脚本。
5. **门禁 preflight 与单测的依赖锁定正则不接受预发布后缀**，导致新增 `0.1.5-rc.1` 类型依赖后报"未锁定精确版本"。两处都改为允许 semver 预发布而仍拒绝 `^ ~ *` 与区间。
