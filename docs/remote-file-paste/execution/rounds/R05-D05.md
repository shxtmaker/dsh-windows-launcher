## 关键侦察结论（决定了判据形态）

1. **CLI 拒绝 `--host 0.0.0.0`**（dsh-web-app 显式拦截，理由是会把 RCE 暴露到网络），而 webserver 的 `config.host` schema 只接受 `127.0.0.1 | 0.0.0.0`。因此夹具改为在 profile patch 中写 `host: '0.0.0.0'`（与生产 profile 的 managed block 同款），访问仍走具体私网地址。
2. **Harness 的 RPC 走 WebSocket**（`connection.rpc.call('/api', endpoint)`），不是 REST。`/remote` 是 HTTP 代理，因此可代理的是 HTTP 路由。实测可用目标为 `GET /api/present.host`（返回真实宿主名与 fileManager），而非我最初猜的 `session.list`（404）。
3. **`/pair-app` 是官方外壳，本身不含数据**：对任何 `device` 都返回同样的外壳 + 设备捕获脚本，真正的门禁在 `/remote` 代理层。因此"伪造 device 拿不到外壳"是错误判据，已改为断言代理层拒绝。
4. **一次成功的 accept 会把发起方私网 host 加入 `dynamicTrustedHosts`**（设计行为），因此未配对判据必须在任何配对动作**之前**执行，否则会被动态信任放行。
5. **夹具必须复现生产 profile 的 `/api` fence lockdown**。绑定 `0.0.0.0` 会让 SDK 在 `/api` Host 栅栏里自动信任私网 IP 字面量，未配对的 LAN 客户端因此可以直连整套桌面 API。生产 profile 用 `connection.trustedHosts: []` 覆盖掉这一默认；夹具原先没有这一行，导致 H02 实测 `status=200 hostDataLeaked=true`。补齐后为 `403 forbidden`。

### HTTPS 场景（本轮后半完成）

部署形态与生产一致：webserver 本身只提供 HTTP（其 config schema 只接受 `host`/`port`），生产由反向代理做 TLS 终结。因此本轮加了本地 TLS 反向代理 + 测试 CA，而不是给 webserver 加非生产的 TLS 支持。

`fixture:https` **连续两轮 9/9 通过**（TLS origin `https://192.168.3.190:3443`）：

| 判据 | 结果 | 实测值 |
| --- | --- | --- |
| I01 不提供受信任 CA 时 TLS 校验必须失败 | PASS | `UNABLE_TO_VERIFY_LEAF_SIGNATURE` |
| I02 HTTPS 未配对访问 `/remote` 被拒 | PASS | `403` + `unpaired` |
| I03 HTTPS 未配对直连 `/api` 读不到宿主数据 | PASS | `403 hostDataLeaked=false` |
| I04 HTTPS accept：303 且重定向保持 HTTPS | PASS | `httpsRedirect=true`，下发设备 cookie |
| I05 HTTPS cookie 流经 `/remote` | PASS | `200 hasHostData=true` |
| I06 HTTPS 免 Cookie 流（仅设备头） | PASS | `200 hasHostData=true` |
| I07 HTTPS 吊销后拒绝 | PASS | `revoke=200 after=403` |
| I08 HTTPS 与 HTTP 两个 origin 判定一致 | PASS | `https=403 http=403` |
| I09 HTTPS 脱敏 trace 无泄漏 | PASS | 无命中 |

I01 是关键判据：它证明"HTTPS 可用"不是靠 `NODE_TLS_REJECT_UNAUTHORIZED` 或 `rejectUnauthorized:false` 换来的。检查实现只用 `https.request` 的 `ca` 选项**增加**一个受信任 CA，hostname/SAN 校验仍走 Node 默认链；不给 CA 时必然失败。

证据路径：`artifacts/verify-portable/d05-https-evidence.log`、`d05-https-gates.json`、`d05-https-trace.jsonl`（均已脱敏、耐久）。

新增的自身缺陷（HTTPS 阶段，均已修复并重跑）：
6. `pairing-fixture` 的"夹具已存在"判断原先看 `lan-address.txt`，而 `tls-setup.sh` 也会写该文件，导致门禁误判为已建好而跳过安装，服务因缺 profile 直接退出（退出码 1）。改为按 **profile 的 `package.json` 是否存在**判断。
