## 本轮遇到的阻断（已定位到根因）

真实 Chromium 加载夹具页面时 **client 模块加载失败，页面无 composer**，D08 的 UI 判据无法执行。**根因已定位并实证**：

### 根因：bootstrap 脚本标签缺少 `type="module"`

服务端注入的那条 client 模块引导脚本被渲染成**经典脚本**：

```html
<!-- 实际（无 type=module）-->
<script src="/plugins/??@deepseek-ai/dsh-client-modules/client.js&amp;rev=cddf5581d5d5">
<!-- 同一文档里的主入口是正确的 module -->
<script type="module" crossorigin src="./assets/index-BKQ_L1z6.js">
```

而它加载的那份 14.6 MB 合并 bundle **确实含顶层 `import`**，因此按经典脚本解析必然抛
`SyntaxError: Cannot use import statement outside a module`，随后
`failed to import loader entry (@deepseek-ai/dsh-client-hmr)`，页面显示 `Failed to load plugins`。

实测判据链（逐条都有证据，不是推测）：

| 观测 | 结果 |
| --- | --- |
| 出错脚本的 URL 与行号 | `Runtime.exceptionThrown` 给出 URL（`/plugins/??…&rev=03d94c084600`）与 `lineNumber=161538` |
| 该 URL 的响应 | `200`、`text/javascript; charset=utf-8`、`14 616 357` 字节 |
| 该 bundle 的模块语义需求 | **顶层 `import` 1 条、`export` 5 条**、`__ModuleLoader__.load` 55 次 |
| 页面里该脚本的标签 | `<script src="/plugins/??@deepseek-ai/dsh-client-modules/client.js&rev=…">`，**无 `type="module"`** |
| `Debugger.scriptParsed` | 该 bootstrap URL 的 `isModule=false`，而主入口为 module |

**注入路径**：`@deepseek-ai/dsh-client-modules` 通过 `webserver/index-inject` 推入
`kind: 'script-src'` 行（`lib/index.js:421-424`），而 `@deepseek-ai/dsh-host-webserver` 的
`renderRow` 对 `script-src` 渲染为 `<script src="…">`（`lib/index.js:34-37`）——**不带 `type="module"`**。
模板 `@deepseek-ai/dsh-web-frontend/dist/index.html` 本身只含正确的 module 主入口，因此问题不在模板。

### 为什么这属于上游缺陷而非本插件问题

- 失败发生在**任何本插件代码执行之前**（我们的 `__DSH_FILE_UPLOAD__` 已安装，client 模块在 roster 中且不是失败点）。
- 涉及的三个包都不是本仓库的代码：`dsh-client-modules`、`dsh-host-webserver`、CLI 的渲染路径。
- 版本组合为 dsh CLI **0.1.5-rc.1** + 内部包 **0.1.5-rc.2**（D00 已登记该偏离），本缺陷即该偏离的一次具体暴露。

### 最小补丁验证结果（用户指示执行，已完成）

**结论：HTML 渲染层的 `type="module"` 补丁是必要但不充分的——真正的问题更深。**

在**隔离副本**上验证（把 `@deepseek-ai/dsh-host-webserver` 复制到夹具 profile 的 `node_modules`
覆盖解析，改完只影响夹具；已安装原件与生产 profile 全程未改动，验证后副本已删除）：

补丁内容（`renderRow` 的 `script-src` 分支）：

```diff
- markup: `<script src="${escapeHtmlAttribute(row.src)}"><\/script>`
+ markup: `<script type="module" src="${escapeHtmlAttribute(row.src)}"><\/script>`
```

验证结果 2/5：

| 判据 | 结果 | 证据 |
| --- | --- | --- |
| V1 注入的 bootstrap 标签带上 `type="module"` | **PASS** | 实际服务出 `<script type="module" src="/plugins/??@deepseek-ai/dsh-client-modules/client.js&rev=…">` |
| V2 页面不再出现模块加载失败 | FAIL | 仍报 `SyntaxError: Cannot use import statement outside a module` |
| V3 出现 `[data-composer-card]` | FAIL | `cards=0` |
| V4 出现 `input[type=file][multiple]` | FAIL | `multipleFileInputs=0` |
| V5 `__DSH_BOOT_READY__` 存在 | PASS | 骨架脚本仍执行（不代表模块加载成功） |

**补丁不充分的原因（已定位到具体代码）**：报错的那份 14.6 MB 合并 bundle **不是**通过 HTML 里的
`<script>` 标签加载的，而是由 `@deepseek-ai/dsh-client-modules` 在运行时**动态创建经典脚本**加载的：

```js
// node_modules/@deepseek-ai/dsh-client-modules/lib/client.js:145-159
/** Default bundle-load hook: same-origin external classic script. */
const defaultLoadBundle = (url) => new Promise((resolve, reject) => {
  const el = document.createElement("script");   // ← 没有 el.type = "module"
  el.async = true;
  el.src = url;
  ...
});
```

而它加载的那份 bundle 含**顶层 `import` 1 条与 `export` 5 条**（同前一轮实测），
因此在经典脚本语义下必然在第 161538 行解析失败。错误 URL 在打补丁前后**完全一致**，
印证了"失败点不经过 HTML 注入路径"。

**因此这是 `dsh-client-modules` 自身的不一致**：它把各插件的 `client.js` 按 ESM 语法拼进一个
"bundle"，却用经典脚本标签加载。第二处补丁（给该 loader 加 `el.type = "module"`）属于**再改第二个
上游包**，已超出"验证最小补丁"的授权范围，故停在此处交由用户决策。
