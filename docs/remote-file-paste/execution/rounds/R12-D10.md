## 1. 冻结的契约

**消息（11 类，全部 `v≡1`、`additionalProperties:false`）**：`hello`、`capabilities`、`context`、`batch-begin`、`file-begin`、`chunk`、`ack`、`file-end`、`import-result`、`batch-end`、`cancel`。

**身份**：一次粘贴 = 一个 `batchId`；**首期 `operationId` 就是 `batchId`**（不维护两套可漂移身份）。`fileId` 绑定 `targetId` + `documentEpoch` + `composerEpoch` + `sessionId` + `batchId`。`sessionId` 在 schema 中可选（握手期尚不存在），但**状态机对 8 种操作消息强制**：缺失 = `no-session`，不匹配 = `context-changed`。因此"没有有效 sessionId 不接收批次"落在状态机而不是仅靠 schema。

**序号与在途**：`seq` 从**每个文件**的 0 开始，`offset` 连续，最多两块在途（`inFlight ≤ 2`）；`ack` **只证明接收缓冲接受**。

**限额/超时**：20 MiB/文件、10 文件/批、50 MiB/批、4000 万像素、100 MiB/目标暂存、2 目标；256 KiB/块；单条消息 ≤ 512 KiB；握手 5 s / ack 10 s / `file-end`→`import-result` 30 s / 批次空闲 60 s。

**错误码分工**：36 个 `WIRE_ERROR_CODES`（协议拒绝）与 19 个既有 `ERROR_CODES`（报文 `code` 字段）**不混用**；四阶段（原生采集/协议传输/草稿导入/远端上传）沿用既有 `ERROR_STAGES`。

**重放缓存**：键 `documentEpoch:composerEpoch:batchId:fileId`（批级 `fileId` 为空串），容量 64，TTL 120 s，查询时淘汰过期条目；**活动操作被钉住不可淘汰**，容量压力只淘汰已完成条目，无可淘汰时拒绝淘汰并计数（宁超容量也不重放）。

## 2. 状态三义（任务卡验收点）

`transport{idle,buffering,buffered}` 只由 `chunk`/`ack` 改变；`draft{none,staged,failed,partial}` 只由 `import-result` 改变；`upload{none,harness-owned}`。**枚举里根本没有 `ready`/`uploaded`**——上传就绪与发送仍归 Harness。实测：`status:"upload-ready"` 的样本被判 `unknown-enum-value`；语料 G07/G08 断言 ack 之后是 `buffered + none + none`，G10 断言 `import-result staged` 之后是 `staged + harness-owned`。两条对照都做了"三态被顶替必须失败"的负向断言。

## 3. 语料与两侧一致性

- 语料：**37 条 golden**（34 文件，覆盖 11 类消息与边界：256 KiB 满块、`seq=79`、`fileCount=10`、50 MiB 批、20 MiB 文件、0 字节文件、`bufferedBytes=100 MiB`、`inFlight=2`、`submittedItems=2`、以及 chunk/file-end/batch-end/ack 的幂等重放），**49 条 malicious**（覆盖任务卡列出的全部 17 类并额外 18 类，共 **35 个不同拒绝码**；含多余字段 `localPath=/etc/passwd`、绝对路径文件名、跨 `fileId` 的 chunk、`seq` 跳跃/回绕、`batch-end` 之后的迟到 `file-end`、冲突的重复 `file-end`、复用已关闭 `batchId` 等）。
- **两侧读同一份 `schemas/remote-attachments/v1/expected.json`**（每条样本给出 canonical 解码结果或精确拒绝码 + setup 序列 + per-file 断言）：TS `test/unit/wire-corpus.test.mjs` 86/86 通过；C# `tests/DshLauncher.Core.Tests/Attachments/WireCorpusTests.cs` 86/86 通过。这是"互读同一组有效及恶意样本"的落地形式，而不是两套各自为政的测试。
- 额外**跨语言差分**：`test:wire` 把 332 条确定性敌意变异输入的 TS 结论写入 `artifacts/verify-portable/d10-wire-parity-cases.json`，C# `WireParityTests` 逐条比对 ok/拒绝码/canonical 摘要（316 条全部一致）。

## 5. 未验项与已知边界

- Windows 实机 / WebView2 原生消息通路未验（属 Windows 轨道）。
- `schema.json` 未用 JSON-Schema 库做机器校验（不新增依赖）：改以门禁 W08 校验"语料↔schema"的字段集/常量/枚举/整数范围一致，codec 本身即可执行校验器。
- JSON 数字极端形态（`8.0`、`1e2`、超 int32 大整数）未进语料；两端都把非整数形态判 `invalid-field-type`，语料只覆盖常规整数字面量。
- 超时是策略常量 + `checkTimeouts` 纯判定，**没有后台定时器**，需调用方按需驱动。
- C# `AttachmentSession.Apply` 同步（`IncrementalHash`），TS `apply` 因 WebCrypto 为 async；契约一致，API 形态因语言能力而异。
