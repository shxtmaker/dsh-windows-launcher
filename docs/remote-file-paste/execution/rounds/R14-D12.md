## 2. 验收点的实测结论（真实 Chromium，12/12 gates、7/7 负向探针）

- **File 名称/长度/内容正确**：520 KiB 文件按 256 KiB 满块 ×2 + 尾块 ×1 传输，得到真实浏览器 `File`；**在页面里读回字节**，Node 用 `node:crypto` 与源逐字节 + SHA-256 比对一致；该 File 经 `__DSH_ATTACHMENTS_BRIDGE__.importFiles` 进入原生草稿，下一次导入的 `previous` 里出现同一个原生 attachmentId。
- **坏哈希不能导入**：`hash-mismatch` 拒绝，且 `filesConstructed`/`importsInvoked` 都不增加、不产生第二个 File（N1/N2/N7 负向探针均按预期失败）。
- **无 WebCrypto 路径**：夹具 LAN 页面实测 `isSecureContext=false`、`crypto.subtle=undefined`，接收端报 `hashBackend=pure-js`，组装与 SHA-256 校验照常成功；再用 `Object.defineProperty(crypto,'subtle',{value:undefined})` 强制关掉复验一遍，坏哈希仍被拒——代码中**不存在"HTTP 跳过校验"分支**。
- **一次只组装规定数量文件 + 取消回收缓冲**：cancel 前 16 KiB 在缓冲、cancel 后页面内记账回到 **0**（`releasedBytes=16384`），迟到块判 `cancelled` 且不再入缓冲；全程峰值 532480 B ≤ 目标暂存上限，结束后 `bufferedBytes=0`。
- **内存有界**：接收缓冲 ≤ `min(maxStagingBytesPerTarget, 并发组装数 × maxFileBytes)`；Blob 构造后立即丢弃 parts（`bufferedBytes` 归零、`constructedBytes` 记账）。
- **不搞整文件 Base64**：`new File(parts, name, {type})`，parts 就是各块的 `Uint8Array`；四类超限（字段上限 20 MiB+1、生效批次限额、目标暂存上限、累计越界）都在**写入缓冲前**被拒绝。
- **同会话新批次**：不重发 `context`，新 `batchId` 被 `batch-begin` 承认并完整导入（单测 + Chromium G08 都验）；复用旧 `batchId` → `duplicate-operation`，迟到 `file-end` → `batch-closed`；对照 `navigate()` 后仍必须重新 `context`（证明判据不是恒真）。

## 4. 本轮发现并**如实保留**的一个缺陷（未修，附确切修法）

**症状**：`cancel` 之后，**同一会话再也开不了新批次**——`batch-begin` 被永久拒为 `batch-in-progress`。也就是说用户取消一次粘贴后，不刷新页面就无法再贴。

**根因（已定位到行）**：`plugins/dsh-remote-attachments/src/shared/wire/session.ts:383`

```ts
if (this.batch) {
  if (!this.batch.closed) return reject('batch-in-progress', '同一会话已有开放批次')
  return reject('duplicate-operation', '该 batchId 已关闭；重新导入必须生成新的 batchId')
}
```

`cancel` 只把 `batch.cancelled` 置真（`session.ts:249/276/359/439`），**不置 `closed`**，而准入只看 `!closed`，于是被取消的批次永久占用会话。方案原文要求"批次关闭后**新批次必须经 `batch-begin` 承认**"，取消不应让会话报废。

**为什么本轮不修**：正确修法要同时动三处并保持一致——(1) TS `session.ts` 的准入语义（取消视同关闭、且只有**同一** `batchId` 才算重复）；(2) `receiver.ts` 的批次生命周期（它按批次重建 `WireSession` 并内部预热身份，实测改了一处后新批次的 `file-begin` 仍报 `batch-not-open`，需要成体系地改）；(3) C# `AttachmentSession` 镜像与 D10 语料 `expected.json` 的期望（否则两端一致性与语料判据会破）。我按最小改法试改后无法在本轮内把三处一次性验穿，**故完整回退**——半改的契约语义比不改更糟。回退后 `session.ts` 与 D10 交付状态逐字节一致，单测 100/100、D10 语料 86/86 全绿。

**建议处置**：单独立一轮（例如 `R15-D10-fix`）专门修此契约缺陷，判据至少三条：取消后同会话新 `batchId` 被承认并完成导入；复用被取消的 `batchId` 仍拒 `duplicate-operation`；两端（TS/C#）行为一致且语料同步更新。
