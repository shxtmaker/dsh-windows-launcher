## 关键侦察结论

1. **Harness 的 RPC 走 WebSocket**（`connection.rpc.call('/api', endpoint)`），不是 REST；因此不能靠猜 HTTP 路径驱动对话。
2. **CLI 的 `--profile <name> "<task>"` 一次性任务模式**由 `@deepseek-ai/dsh-headless` 提供，profile 模板名为 `headless`（`dsh-app-boot` 的 `PROFILE_TEMPLATES.headless = { bundles: ['@deepseek-ai/dsh-base','@deepseek-ai/dsh-headless'] }`）。这是本轮能真实驱动 agent 循环的关键；`dsh-base` 单独启动只会挂起，不是任务运行器。
3. **provider 协议**为 OpenAI/DeepSeek 兼容的 `POST /chat/completions` 流式 SSE；`llm-deepseek` 的 `config.baseURL` 可指向本地 stub，`apiKeyEnv` 决定凭据来源。
4. **固定版本真实注册 25 个工具**，其中文件读取是 `read`（`file_path`/`offset`/`limit`）与 `read_image`。工具结果回填为 `role: 'tool'` 消息，正文形如 `<path>…</path><type>file</type><content>1: …</content>`；`read_image` 的结果**自带 `sha256:<64hex>`**。
5. **Harness 的对话历史是累积的**：第 4 次请求会同时带上第 1 次与第 2 次的工具结果。最初按"每次请求遍历所有 tool 消息"计数，导致同一结果被重复统计；改为只记录相对上次新增的结果。

## 本轮修复的自身缺陷

1. **`resolveStep` 会重复下发同一步骤**：原逻辑把"结果尚未返回"也当作未满足，导致同一 `read` 被下发两次。改为只依据真实工具结果里的期望是否出现来推进。
2. **工具结果重复计数**：Harness 的请求携带累积历史，原逻辑每次遍历全部 `tool` 消息，把同一结果记了三次。改为只记录新增部分。
3. **P06 选错了结果对象**：原先在拼接后的全部结果里做行号剥离，把 `read_image` 的描述行也算进去（重建 8 行 vs 期望 4 行）。改为只取 `<type>file</type>` 的文本结果。
4. **P06 最初用"每行都出现在重建结果里"判定**，无法发现顺序错乱或重复；改为逐行按序号比对 + 整体哈希核对。
5. **`run-provider-gates.mjs` 的 `pluginRoot` 少算一层**（文件位于 `tests/fixtures/provider/`，需上三层）。
6. 一次误用 `pkill -f "provider-stub"` 把自己的 shell 也匹配掉了（命令行含该字符串）。后续改为把诊断逻辑写进脚本文件、按脚本绝对路径精确匹配。
