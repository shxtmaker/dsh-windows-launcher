## 1. 上一轮结论被证伪：这不是上游缺陷

上一轮的最小补丁实验只做了一半就停了（`V1` 通过、`V2`–`V4` 仍失败），本轮把原因追到底。

### 1.1 补丁不充分的原因

`@deepseek-ai/dsh-client-modules` 的批次运输链是：

```js
// lib/index.js:183 —— combo URL：把同一 phase 各包的 client.js 列成一条 URL
const comboUrl = (ids, rev) => `/plugins/??${ids.map((id) => `${id}/client.js`).join(',')}&rev=${rev}`;

// lib/index.js:205-215 —— comboSource()：**只剥 sourcemap 尾注**，然后原始字节首尾相接
let source = record.bundle.toString('utf8');
source = source.replace(SOURCE_URL_TRAILER, '').replace(SOURCE_MAP_TRAILER, '');
```

也就是说：批次的字节内容 = 各包 `client.js` 的**原文拼接，没有任何 ESM→CJS 变换**。而两个 phase 的运输方式不同：

| phase | 注入行 | HTML 形态 | 加载方式 |
| --- | --- | --- | --- |
| bootstrap | `kind:'script-src'` | `<script src=…>` | 经典脚本（静态标签） |
| application | `kind:'script-preload'` | `<link rel="preload" as="script" href=…>` | 运行时由 `defaultLoadBundle` 以**经典脚本**动态插入 |

```js
// dsh-client-modules/lib/client.js:145-159 —— 注释自述 "same-origin external classic script"
const defaultLoadBundle = (url) => new Promise((resolve, reject) => {
  const el = document.createElement("script");
  el.async = true; el.src = url;              // 经典脚本，这是**设计**，不是缺陷
  …
});
```

上一轮打的补丁改的是 `host-webserver` 对 `script-src` 的 HTML 渲染。失败的那 14.6 MB 资源根本**不经过** HTML 注入路径，所以补丁改对了地方却改错了对象——`V1` 通过而 `V2`–`V4` 依旧失败，错误 URL 前后完全一致。

### 1.2 真正的根因：本包 client 入口是裸 ESM

契约（`dsh-client-modules/lib/index.js:16-23` 自述）是：每个 client 包在磁盘上的入口必须**已经是**经典包裹形态——

```js
window.__ModuleLoader__.load({ id: '<包名>', factory: (require) => { …; return module.exports } })
```

官方包全部如此（顶层 `import`/`export` 计数为 **0**）：

| 包 | 字节 | 顶层 import | 顶层 export | 首行 |
| --- | --- | --- | --- | --- |
| `dsh-client-hmr` | 4589 | 0 | 0 | `window.__ModuleLoader__.load({` |
| `dsh-client-modules` | 18621 | 0 | 0 | 同上 |
| `dsh-client-ui-conversation` | 647101 | 0 | 0 | 同上 |
| `dsh-client-ui-workspace` | 130113 | 0 | 0 | 同上 |
| **本包（修复前）** | 1787 | **1** | **5** | `/** 注释 */` |

本包入口是 `tsc` 直出的 ESM，于是它把**所在整批**变成语法错误。

### 1.3 决定性证据（HTTP-only，无需浏览器）

新增 `tests/fixtures/bundle-purity-probe.mjs`，直接对服务端字节判定。修复前：

```
[PASS] P1 __DSH_BOOT__ 图可解析且本插件在图中 — batches=2 entries=57
[FAIL] P2 本插件 client.js 已是经典包裹形式 — bytes=1787 顶层ESM语句=6 首个@L14: import { PACKAGE_NAME, … } from './shared/capabilities.js';
[FAIL] P3 所在批次顶层 ESM 计数为 0 — phase=application bytes=14616357 段数=55 顶层ESM语句=6
[FAIL] P4 每个声明条目对应一个包裹段 — 段数=55 批内声明条目=56
[PASS] P5 批内 id 一致
```

三条互相独立的证据闭合到同一结论：

1. **行号吻合**：批次第 161539 行（1-based）正是本包文件的注释块紧接裸 `import`；上一轮 Chromium 报的 `lineNumber=161538` 是 0-based —— 同一个位置。
2. **段数差一**：56 个声明条目只解析出 55 个 `window.__ModuleLoader__.load({` 段，缺的正是本包。
3. **语句计数吻合**：整批 6 条顶层 ESM 语句，与本包入口的 1 import + 5 export 逐条对应。

即：**页面报的 `SyntaxError` 是本包自己造成的**，`Failed to load plugins` 是该批 56 个包一起陪葬的结果。

## 2. 真实修复

### 2.1 构建：产出经典包裹形态（`scripts/build-client-bundle.mjs`，新增）

- 目的是让服务出去的入口满足契约，同时**不引入新依赖、不手写 ESM→CJS 改写**：用已有的 `typescript` 依赖，`ts.transpileModule` → CommonJS 逐个编译 client 半区模块，再套一层本包自己的极小模块注册表与 `__ModuleLoader__.load` 包裹。
- 相对依赖全部内联；裸模块名转发给外层 loader 的 `require`（与官方包一致）。
- 硬校验：顶层残留 `import`/`export` 即失败；注册次数必须恰好 1；产物必须能过 `vm.Script` 语法检查。
- 源文件布局调整：`src/client.ts` → `src/client/index.ts`，让 `tsc` 的 ESM 产物落到 `lib/client/index.js`（供单测），把 `lib/client.js` 这个**服务路径**让给生成的经典包裹产物。`package.json` 的 `exports['./client'].types` 随之指向 `./lib/types/client/index.d.ts`。
- 过程中修掉一个真实缺陷：模块包裹的第三个形参**必须**叫 `require`（不能用 `__require`），否则 `tsc` 产物里的自由变量 `require(…)` 会闭包到外层 loader 的 `require`，相对依赖全部外泄。

### 2.2 第二个真实缺陷：client 半区的 `apply` 参数顺序错误

批次纯净后页面报错变成指名本包：

```
failed to apply loader entry (@shxtmaker/dsh-remote-attachments): cannot get property "enabled" without inject
```

cordis 的调用约定是 `apply(ctx, config)`（`dsh-client-hmr/lib/client.js:62` 即 `function apply(ctx)`），ctx 是代理对象，读未声明属性会抛错。本包 host 半区写对了（`src/host/index.ts:78` `apply(ctx: Context, config: HostConfig = {})`），但 client 半区写成了 `apply(config = {})`——把 ctx 当配置读，于是整个 loader entry 挂载失败。已改为 `apply(ctx: ClientContext, config: ClientConfig = {})`，并新增最小结构类型 `ClientContext`（只声明本半区真正会用的 `logger`），避免把 host 侧服务形状带进 client 产物。

### 2.3 顺带修掉一个夹具竞态

`tests/fixtures/lib.mjs` 的 `waitForReady` 轮询的是**共享日志文件**，上一次运行残留的 `dsh web:` 行会让它在服务真正监听之前就判定"已就绪"（本轮实测触发 `ECONNREFUSED` 竞态）。已改为 `startService` 启动时按运行截断日志。
