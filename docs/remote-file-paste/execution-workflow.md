# 分轮执行与恢复规则

方案版本：2.0。适用于本目录全部 DEV 任务及配套 DeepSeek Harness 提示词。用户要求分轮实施，本文件是执行约束，不是对本次方案编写工作的限制。

## 1. 一轮的定义

一轮从用户明确发出的执行指令开始，例如首次粘贴实施提示词、发送“继续”或“执行 D07”。模型自动续写、工具返回、上下文压缩、子代理回复、定时唤醒均不构成新一轮。用户询问进度或技术问题，只需回答，不因此获得执行下一任务的指令。

首轮 R00 只执行 D00：读取资料、核对基线、检查已有变更、建立执行台账与交接记录。允许写上述计划及记录，不修改业务代码，不顺带执行 D01。已有台账时先恢复，不能清空后假装首次执行。

此后每轮最多执行一个依赖已满足的 DEV 叶任务。任务可跨多轮，不能为了“一轮完成”削减验收。当前任务完成后必须记录并结束；即使时间、上下文和工具额度充足，也不转入下一任务。全部开发任务结束后停止，普通“继续”不能自动启动 Windows 验证或发布。

## 2. 读取与调度

每轮依次读取：

1. 仓库 AGENTS.md、CONTEXT.md 和当前 git 状态。
2. [技术方案](implementation-plan.md)、[任务索引](task-index.md)和本文件。
3. [task-graph.json](task-graph.json)、[execution/state.json](execution/state.json)、[最近交接](execution/handoff.md)。
4. 所选任务卡及它引用的专项验证要求；恢复轮同时读取该任务上轮日志。

task-graph.json 保存任务定义、依赖和卡片路径；state.json 是任务动态状态的唯一真值；任务索引是阅读视图，不另存一份状态。每次完成修改后核对三者一致性。

选择规则：

- 有未完成的 in_progress/partial 任务，默认继续该任务。先核实中断后文件、进程和测试是否仍在运行，不能重复启动写入。
- 上轮 blocked 时，先核实阻断是否解除；未解除且存在其他依赖已满足的独立任务，可以在本次新的执行轮选择编号最小的可执行任务，保留原阻断。
- 无未完成任务时，选择依赖全部完成的最小编号 todo 叶任务。
- 用户指定任务时优先尊重指定；依赖未满足则报告具体依赖并结束，不自动改做另一个任务。
- 选择后先登记 currentTask、round 和 in_progress，再开始工作；本轮不切换到第二个任务。

编号表示建议顺序，依赖图表示硬性前置。不同任务即使理论上可并行，也不在同轮并行开发。允许子代理承担当前任务内的只读调查、独立实现部分或检查；子代理必须受同一任务范围约束。返回本轮最终答复前须收拢结果并停止所有会继续写入的代理、构建或后台任务，不创建自动接续的定时任务。

## 3. 任务完成、拆分和局部修复

当前任务允许修改其列明的范围，以及让其直接验收成立所必需的最小关联代码、配置、测试和说明。跨模块依赖暴露出更大工程时，不能以“修复前置”为名顺带完成其他任务。

任务太大或依赖失实时，本轮只登记拆分或依赖调整，不开始执行多个子任务。创建 Dxx.1、Dxx.2 等子卡，补充依赖和验收，将父任务标记 split；下轮从依赖满足的子任务开始。父任务保留 split 状态，其完成度由所有子任务计算；下游只有在全部叶子 done 且证据有效时才算依赖满足。父项不再被选为执行任务，禁止依赖循环。

task-graph.json 中子任务使用可选 parentId 指向父任务，父项不再保存另一份 children 列表；当前初始叶任务省略 parentId。子任务必须继承父任务原始前置，或者通过兄弟任务依赖传递满足这些前置；不得依赖自己的 split 父项或祖先。下游原有 dependsOn 可以继续引用父项，解析时递归检查全部后代叶任务有效 done。新增子任务同时创建任务卡和 state 条目，更新索引并检查父子关系与依赖均无环。

发现阻断时保存已有合法成果，列出可复现问题与最小解除条件并结束。缺少 Windows 实机不会阻断任何 DEV 任务；Windows 代码仍应写完整，实际运行证据转入 WindowsPending。真实 Linux 宿主集成失败则不能用 mock 或未执行的 Windows 计划替代。

当前任务直接暴露的局部缺陷可在本轮修复并重跑相关检查。新发现的其他任务缺陷应登记后续任务或恢复原任务状态，不能扩大本轮范围。不得为保持 done 而删除测试、吞掉失败或修改功能验收标准。

## 4. 状态与证据

任务状态定义：

| 状态 | 含义 | 下轮动作 |
| --- | --- | --- |
| todo | 尚未开始 | 依赖满足后可选择 |
| in_progress | 当前正在执行 | 核实现场后恢复 |
| partial | 已保存部分成果，仍有可执行步骤 | 继续同一任务 |
| blocked | 有明确外部或技术阻断，当前无法继续 | 核实解除条件，或另选独立就绪任务 |
| done | 本任务范围的交付和要求验证均有有效证据 | 不自动执行下一任务 |
| split | 已分为登记的子任务 | 按叶任务调度，完成度汇总计算 |

中断是轮次结果，不自动等于测试失败或 blocked。进程被打断、工具结果丢失时，记录 interrupted，任务根据可恢复程度保持 in_progress 或转 partial；不得猜测退出码。

state.json 的每项至少保留 lastRound、checkpoint、remaining、blocker 和 evidence。evidence 记录命令、运行平台、结果、退出码、实际用例数、报告路径、被测提交或工作树摘要；notRun 不能写为 pass。已有报告因后续相关代码、依赖或测试配置改变而失效时，标为 stale，并将受影响 done 任务恢复 partial 或登记明确复验叶任务，重新计算后续门禁；无关文档更名不要求重跑全部测试。

项目状态独立于单项任务：

- developmentStatus：notStarted / inProgress / blocked / ready。
- windowsStatus：pending / inProgress / passed / failed。
- releaseEligible：只有 Linux 与独立 Windows 正式门禁均满足时才能为 true；该字段不授权发布。

初始台账全部 todo、developmentStatus=notStarted、windowsStatus=pending、releaseEligible=false。本次编写方案不意味着任何代码任务已完成。D24 的完整 Linux 门禁与 D25 交接均完成后，方可设置 developmentStatus=ready 并对外报告 DevelopmentReady。

## 5. 每轮持久化

每轮结束前按顺序：

1. 停止本轮会继续写入的后台工作，检查实际变更并保护用户已有改动。
2. 保存 artifacts 中的验证证据，写 execution/rounds/Rxx-Dyy.md 轮次记录。
3. 更新 state.json 的状态、剩余步骤、阻断与证据。
4. 更新 execution/handoff.md，写明最近轮次、当前候选摘要、恢复入口和下一建议。
5. 核对 JSON、依赖与链接有效，再返回本轮结论。不得自行发送“继续”。

如果意外中断发生在步骤之间，下轮以真实文件和证据校正台账，记录修复原因；不得仅根据状态文件把未完成代码记为完成。计划文档和日志不得保存凭据、配对链接、文件内容或完整私人路径。

轮次记录模板：

```markdown
# Rxx / Dyy
用户执行指令：
方案版本与被测候选摘要：
本轮范围：
执行前状态：
实际变更：
实际验证：命令、平台、退出码、用例数、报告路径
未执行项与所属轨道：
本轮结果：done / partial / blocked / split / interrupted
已保留成果：
剩余步骤或解除条件：
本轮仍运行的后台写入：无
下一轮建议：仅建议，不自动执行
```

每轮回复采用固定内容：当前任务及状态、完成内容、实际验证与未验项、持久化记录路径、下一轮建议。无需再次请求对已选任务的执行许可；结束当前轮本身就是用户要求的节奏。

## 6. Windows 独立轨道

DEV 图中没有 Windows 实机依赖。D25 只交付候选源码、插件包、Linux 报告、兼容清单和待验项目，不执行 Windows 安装或实机操作。

用户明确要求开始实机验证后，按 [Windows 专项分轮表](windows-validation-plan.md#9-windows-独立分轮安排)选择一个 W 阶段。Windows 验证另存 evidence，不覆盖 Linux 报告。实机发现缺陷时登记独立修复任务，并在后续执行轮修复、重验受影响 Linux 项和 Windows 项；不得把 WindowsPending 改成通过以结束工作。
